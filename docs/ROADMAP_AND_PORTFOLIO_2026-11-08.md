# RoboDataOps 完整版本与招聘展示规划

日期：2026 年 11 月 8 日，Asia/Shanghai。  
状态：后续规划；本文中的工时、验证规模、页面和视频为拟定工作，不代表已经实施。

## 1 建议的终点

先完成可供求职展示的 V1.0，再按真实团队需求扩展商业版本。求职 V1.0 应达到：陌生访问者能快速理解用户问题，体验一条决策流程，查看实际验证结果，并追溯到核心代码、测试和本人贡献。

建议采用四项互相连接的交付物：HTML 项目案例页、90 秒真实操作视频、可操作演示、带版本的 GitHub 代码与证据。网页负责按读者兴趣组织内容；视频负责连续讲解；演示负责实际体验；仓库负责核查。

## 2 当前基线与缺口

现有验证记录包含52项通过测试、核心包90.44%行覆盖率、100个独立枚举情景、300次策略约束检查，以及100条/16,048帧/5任务的固定公开样本。这里是现有报告记录，本次规划未重跑测试。

| 方面 | 已有 | 下一步缺口 |
|---|---|---|
| 具身数据处理 | episode边界、schema、索引、时间、动作维度、任务映射 | 视频证据、动作单位/控制语义的显式契约、第二来源适配 |
| 验收决策 | 系统证据、人工复核、互斥状态、任务缺口 | 批量复核、撤销入口、规则与快照差异解释 |
| 补采规划 | 均分、贪心、MILP、独立可行性核对、版本快照 | 情景保存、反事实解释、成品率敏感性 |
| 到货闭环 | 同源同契约验收与重复计功防护 | 自动生成累计分析快照并回算总缺口 |
| 工程 | 锁依赖、CLI、测试、浏览器检查、wheel | 首个真实提交/发布基线、远端CI、公开演示、版本对齐 |
| 用户与业务 | PRD、假设、用户测试协议 | 真实访谈、任务对照、实际反馈驱动迭代 |
| 策略收益 | 有后续实验协议 | Linux仿真、训练seed、rollout结果 |
| 招聘展示 | README、截图、代码入口、验证报告 | 一个可分享入口、连续演示、个人能力与证据的对应关系 |

当前工作区文件仍为未跟踪状态。版本治理阶段应建立真实的首版基线，再保存后续实际修改；不要补造历史提交或把工程审查记录写成用户访谈。

## 3 招聘 V1.0 应优先完善什么

### 3.1 真实轨迹证据

先选择5–10条有代表性的轨迹，为证据区增加视频片段与状态/动作曲线联动。通过metadata定位episode在共享视频中的时间区间；显示相机、偏移、抽查范围和未检查状态。

新增文件缺失、解码失败、黑帧/冻结等可解释检查。黑帧或冻结在没有任务语义时可以是复核信号，不直接表示整条轨迹没有学习价值。动作单位、绝对/增量控制、时钟信息没有证据时保持未知。

验收：用户从一项发现跳转到正确片段；合法静止有负例；未下载、无法解码与未发现异常分别显示；抽查不会被描述成全量视频通过。

LeRobot官方已有查看器与数据工具，可优先复用其能力。本人新增实现重点仍是证据与验收/补采决策的连接。[官方工具](https://huggingface.co/docs/lerobot/using_dataset_tools)

### 3.2 自动累计快照

到货验收后生成派生的累计分析快照，保留原始文件和父快照。对跨批次源身份去重，记录新增计入、重复、待复核与排除原因，再重新计算全部任务缺口。

不能直接拼接不同平台、动作语义或schema的数据。跨revision的同源episode、重复提交、部分复核和撤销都需要明确行为。派生分析快照与可供训练的正式数据集分别命名。

验收：相同到货重复导入不增加数量；新增数据在总覆盖中只计一次；旧方案和旧报告保持不变；用户能比较两个快照的变化及原因。

### 3.3 更完整的任务与数据契约

让目标、优先级、单价、产能、平台和验收要求有明确的来源。逐项标记为模拟、用户输入或历史估计。支持保存/加载情景，导出前显示仍待确认的责任人、周期和动作语义。

增加一个小型第二来源，例如ALOHA，展示维度、FPS和相机差异能够由profile处理。目标是证明适配边界清楚，不追求首版覆盖大量格式。

### 3.4 决策解释

支持预算变化、单价变化或产能变化的情景对比。要解释“为何没有分配某任务”，先做放宽相关约束的反事实重算，再判断它是否真是瓶颈。

成品率有依据时，增加乐观/基准/悲观分析。使用每次尝试成本时，不将期望成本视为确定交付保证。保留贪心与优化打平的结果。

### 3.5 真实用户与人工标签

邀请3–5位相关人员完成定位异常、追溯缺口、预算变化和解释导出清单的任务。与原流程比较，平衡顺序，记录时间、关键错误、求助和原话。

对30–50条原始样本建立人工标签，条件允许时双人审阅，并包含未告警样本。真实缺陷不足时，不估计缺乏依据的召回率。开发与冻结集合先按原episode/session分组，再生成变体。

至少保留一次真实“观察—决策—代码修改—复测”。若参与者来自相邻领域，说明其角色与结论范围。

### 3.6 发布与复现

建立Git基线、版本标签、变更记录与真实远端CI。新环境按照README复现默认流程；公开演示使用隔离会话、固定样本、重置入口和清楚的资源限制。

招聘页、视频、演示和代码标记同一release。页面上的测试、数据规模和验证数字从报告构建，不手工复制后长期不更新。公开演示不能仅提供127.0.0.1链接。

## 4 排期与投入

建议新增50–80小时，按每周15–20小时安排约4–6周；访谈协调、素材和计算资源会影响日历时间。前两项先交付，让项目尽早可展示，再持续补证据。

| 工作包 | 拟定投入 | 产物与验收 |
|---|---:|---|
| 首版基线与主案例 | 4–6h | 真实Git基线、发布清单、完整演示输入与预期 |
| HTML案例页 | 8–12h | 桌面/手机可读，三层阅读路径，证据和代码链接可达 |
| 90秒视频 | 4–6h | 真实录屏、清晰字幕、数据来源与版本标注 |
| 视频证据与profile | 10–16h | 小样本片段定位、契约与负例；第二来源按范围选做 |
| 累计快照闭环 | 8–12h | 回流去重、累计统计、差异说明与回归 |
| 用户/人工验证与迭代 | 12–20h | 实际记录、对照结果、至少一次修改与复测 |
| 发布整合 | 4–8h | 远端CI、演示、视频定稿、证据版本一致 |

第1周：发布基线、确定演示故事、网页初版和视频粗稿。

第2–3周：视频证据、契约、回流累计与相关回归，同时开始预约试用。

第4周：执行真实用户任务和人工审阅，修复观察到的问题。

第5–6周：定稿网页与视频、公开演示和V1.0发布。材料可以提前使用，实际结果补齐后再更新版本。

## 5 HTML介绍网页怎么设计

建议制作“可核查的项目案例页”。以产品工作流为主线，展示用户、决策、代码和证据。

### 5.1 三层阅读

| 阅读路径 | 目标 | 内容 |
|---|---|---|
| 30秒 | 知道用户和产品结果 | 一句话定位、真实界面、三个入口 |
| 2分钟 | 看懂一次决策 | 90秒视频、可选步骤演示、输入到输出 |
| 5–10分钟 | 核查能力与取舍 | 核心代码、测试、架构、实验、一次迭代和局限 |

这些是页面设计目标，不是关于所有招聘者浏览习惯的统计结论。

### 5.2 页面结构

1. 首屏：RoboDataOps名称、一句话用户价值、真实界面；入口为看90秒演示、试用产品、查看代码与证据。
2. 用户场景：收到数据后如何验收与决定下一轮采集，展示最近实际案例或明确标记的情景。
3. 一次完整决策：问题证据→复核→数量变化→预算比较→补采清单→回流。
4. 具身数据判断：episode边界、动作语义、技术通过与任务成功、静止示范与误报、数量目标与能力。
5. 核心代码导览：quality.py、coverage.sql、planning.py与对应测试，链接到同一固定版本。
6. 验证：当前软件结果、真实用户结果、尚未验证的事项分别列出，说明样本和分母。
7. 一次迭代：原始观察、优先级判断、修改、复测；当前可先展示真实工程缺陷修复，用户研究完成后补充用户案例。
8. 贡献与下一步：本人实际主导、AI辅助和开源复用的范围；补充简历中的对应项目链接。

建议提供中文和英文版本。内容共用结构化数据，避免中英文数字和状态不一致。

### 5.3 适合的小交互

- 点击轨迹问题，展示证据与状态归约，讲明为什么不重复扣数。
- 调整一个小型情景预算，查看均分、贪心与优化的分配变化，明确这是教学/模拟情景。
- 在能力标签间切换，跳转到相应代码、测试和设计记录。
- 点击测试数字，打开报告及其版本，而非只显示徽章。

真实工作台提供实际操作；介绍页中的解释性动效不冒充实时产品结果。视频不自动有声播放，手机可直接阅读截图与文字。

### 5.4 部署

静态介绍页可使用GitHub Pages，它托管HTML/CSS/JavaScript。Streamlit工作台另选支持Python的部署服务；GitHub Pages本身不运行该后端。[GitHub Pages文档](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

Streamlit Community Cloud是演示候选，正式发布前验证依赖、会话隔离、文件访问、固定样本与冷启动。不要在尚未部署时填入看似可用的线上地址。[部署文档](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app)

## 6 视频怎么做

建议用90秒真实产品录屏作为主视频，少量动画解释概念，字幕贯穿。后续如需要深度工程展示，再增加4–6分钟代码讲解。

### 6.1 90秒分镜

| 时间 | 画面 | 讲解重点 |
|---|---|---|
| 0–10秒 | 数据批次、任务和预算 | 谁在什么场景下需要决定什么 |
| 10–25秒 | 定位一条异常轨迹与原始证据 | episode、字段、区间和可解释规则 |
| 25–40秒 | 驳回一项不成立的信号，返回覆盖表 | 正常等待可能有价值；人工结论如何改变计入口径 |
| 40–60秒 | 调整预算，比较三种分配，导出 | 目标、约束、残余缺口和业务取舍 |
| 60–75秒 | 三个代码入口、回归与枚举结果 | Python/SQL/优化与工程验证 |
| 75–90秒 | 贡献范围、边界、网页/仓库入口 | 本人实际工作、可核查证据与下一步 |

所有数字以录制时对应release为准。合成故障、公开数据和模拟成本始终有标记。未做用户测试时，视频不宣称效率提升；未做训练时不宣称策略收益。

### 6.2 动画的作用

适合解释：一条episode包含哪些信号；发现如何经过人工复核进入数量统计；预算如何变成整数分配。其余画面优先展示真实产品和实际代码。

可以先复用现有Playwright浏览器流程进行确定性录屏；官方支持浏览器测试视频录制。[Playwright视频文档](https://playwright.dev/python/docs/videos)

确需较复杂片头/概念动画时，再评估HTML时间轴动画工具。先做真实录屏粗稿，再决定动画是否值得投入；避免主界面更新后大量重做素材。

附加物可以是8–12秒的静音动图，放在README；详细讲解视频另按工程面试需要制作，不要求一次把全部格式做完。

## 7 把能力连接到证据

| 能力 | 建议呈现的判断 | 当前或计划证据 |
|---|---|---|
| 具身数据思维 | 文件不等于episode、低运动不等于无价值、动作维度不等于语义一致 | ingest/contracts/quality、正常等待负例、原契约回流反例 |
| 产品能力 | 用户、任务、验收口径、优先级、修复与补采的区分 | PRD、状态工作流、真实用户任务与迭代 |
| 代码能力 | 数据处理、SQL聚合、清楚边界、输入校验与求解状态 | 三个代码入口、可运行CLI、本人可解释的修改 |
| 工程能力 | 版本、复现、回归、打包与并发一致性 | 锁文件、checksum、测试、并发反例、发布与远端CI |
| 定量决策 | 目标为何这样定义、成本和权重如何影响结果 | 数学模型、独立oracle、敏感性、打平案例 |
| 用户与商业思维 | 哪一步实际节省时间、什么情况下不值得使用 | 待执行用户对照、交付周期和真实成本记录 |
| 沟通与学习 | 能向不同读者解释同一套系统 | 双语案例页、视频、现场讲解与变更演练 |

现有测试和代码能证明软件的一部分质量。个人能力还需要本人能解释、修改、复现并回答追问。项目使用AI辅助开发，应按实际情况标注贡献，避免把AI生成或开源求解器描述为本人独立编写/发明。

建议准备三次亲自参与并记录的演练：增加一条规则及合法负例；修改一项SQL统计且证明不重计；增加一项业务约束并解释软目标与不可行性。每次保留需求、修改、失败、修复与复现记录。

## 8 商业完整版本放在哪一阶段

在招聘V1.0之后，按试点需要增加：多人权限与服务端数据库、对象存储和分块任务、后台检查与进度恢复、供应商报价与排期、成品率与成本不确定性，以及策略失败切片回接目标。

若目标岗位更偏算法或研究，优先做小型策略实验：2–4任务、固定BC/ACT、至少3个训练seed，固定评测初始状态；质检筛选和预算分配分开消融。先试跑估资源，再扩大rollout。仿真结论不外推为真机收益。

是否继续商业化，由重复使用、真实交付与支付证据决定，不以功能数量定义完成。

## 9 下一轮建议交付

先冻结可复现基线与一条主演示案例，制作HTML案例页初版和90秒录屏粗稿；同时预约用户测试。随后增加视频证据与累计快照，依据反馈迭代，最后统一发布V1.0并更新所有证据链接。

V1.0结束条件：陌生读者能说清用户与决策；目标用户能完成关键流程；一次真实反馈有修改和复测；代码/测试/报告可追溯；网页/视频/演示与同一release一致；所有尚未验证的收益标注清楚。
